Estudo de Caso Simulado

Conheçam o George

George é um desenvolvedor de software que utiliza inteligência artificial diariamente para acelerar sua produtividade. Num fim de semana, ele decide tirar do papel uma ideia ambiciosa: criar uma rede social centrada em comunidades de nicho — um espaço autêntico para o público jovem.

A estratégia de George é simples: construir rápido, publicar cedo e validar a ideia com usuários reais antes de investir em infraestrutura robusta.

"Se eu conseguir fazer funcionar neste fim de semana, publico na segunda-feira. O mercado vai me dizer se a ideia presta."

Investigando a Causa-Raiz do Gargalo

George analisa os logs e métricas do PostgreSQL para entender o que está degradando a performance:

Passo 1 — Monitoramento de CPU

$ top -p $(pgrep postgres) PostgreSQL CPU: 98.7% · I/O Wait: 64%

A CPU do servidor de banco de dados opera no limite. A maior parte do tempo é gasta aguardando operações de disco (I/O).

Passo 2 — Consultas Bloqueadas por Locks

SELECT count(*) FROM pg_stat_activity WHERE wait_event_type = 'Lock'; 342 conexões aguardando liberação de locks

As transações de escrita (INSERT de posts, UPDATE de likes) geram bloqueios que impedem as leituras (SELECT do feed) de serem executadas.

Passo 3 — Proporção Leitura vs. Escrita

Leitura: 89% das queries · Escrita: 11% das queries Ambas disputam o mesmo recurso físico de disco e memória

Operações de natureza completamente distinta — pesadas em leitura e sensíveis em escrita — competem pela mesma instância de banco, gerando contenção mútua.

Diagnóstico Final

O backend foi escalado horizontalmente (múltiplos contêineres), mas o banco de dados permaneceu como ponto único de gargalo. O problema não é de código — é arquitetural.

Padrão Arquitetural

CQRS — Command Query Responsibility Segregation

Command
Query
Responsibility
Segregation

O CQRS é um padrão de arquitetura que separa as operações de escrita (Commands) das operações de leitura (Queries) em modelos, serviços e — quando necessário — bancos de dados distintos.

Command Side (Escrita)

Focado na integridade transacional. Executa validações de regras de negócio e grava em banco normalizado otimizado para consistência (ACID).

Query Side (Leitura)

Focado em velocidade de resposta. Consulta bancos desnormalizados, caches e índices de busca pré-computados — sem JOINs complexos.

Linha do Tempo do Padrão
1988 Bertrand Meyer introduz o CQS (Command-Query Separation) em Object-Oriented Software Construction.
2009 Udi Dahan publica Clarified CQRS, socializando a aplicação do padrão em sistemas distribuídos.
2010 Greg Young formaliza o termo CQRS em seus documentos técnicos, integrando-o ao Domain-Driven Design (DDD).
2011 Martin Fowler publica análise definitiva sobre o padrão em martinfowler.com.
Redesenho Arquitetural

O Sistema do George com CQRS

Resultado

Com a separação dos fluxos de leitura e escrita, a latência do feed caiu de 1.200 ms para menos de 50 ms. Os bloqueios de banco desapareceram.

Trade-offs do CQRS

Toda decisão arquitetural é uma troca consciente. O CQRS resolve a contenção, mas adiciona:

  • Necessidade de sincronização entre os bancos de escrita e leitura.
  • Dados duplicados e desnormalizados no lado de leitura.
  • Complexidade operacional aumentada (mais componentes para monitorar).
  • Transição de consistência forte para consistência eventual.

Fundamentos Teóricos

Teorema CAP e Consistência Eventual

C Consistência Todos veem o mesmo dado ao mesmo tempo
A Disponibilidade O sistema sempre responde, mesmo sob falha parcial
P Tolerância a Partições O sistema funciona apesar de falhas de rede

Em caso de partição de rede, é necessário escolher entre C ou A.

O CQRS opta por A + P (disponibilidade), aceitando consistência eventual.

ACID (Escrita)
  • Atomicidade: tudo ou nada
  • Consistência: estado sempre válido
  • Isolamento: transações isoladas (locks)
  • Durabilidade: gravação permanente
VS
BASE (Leitura)
  • Basically Available: o sistema responde
  • Soft State: dados podem flutuar temporariamente
  • Eventual Consistency: converge para o estado correto

Analogia Cotidiana

Quando você posta uma foto no Instagram, seus seguidores não veem instantaneamente no mesmo milissegundo. O feed de cada um converge para o estado correto em poucos segundos. Isso é consistência eventual — e é perfeitamente aceitável para interações humanas.

Padrão Complementar

Event Sourcing

O Event Sourcing armazena cada alteração de estado como um evento imutável em um log sequencial (Event Store). O estado atual do sistema é derivado da reprodução ordenada dos eventos.

Vantagens do modelo

  • Auditoria completa: cada mudança é registrada como fato histórico.
  • Replay de estado: é possível reconstruir qualquer visão do banco a partir do zero.
  • Desacoplamento temporal: escrita e leitura podem ser processadas em momentos diferentes.
Histórico
2005 Martin Fowler formaliza o padrão Event Sourcing.
2006 Greg Young integra Event Sourcing ao CQRS.
2011 Apache Kafka populariza o log distribuído de eventos (Kreps et al.).

Adoção na Indústria

Casos Reais de Aplicação do CQRS

Amazon — DynamoDB (2004 – 2007)
Problema: O catálogo de produtos cresceu exponencialmente. O banco Oracle centralizado sofria com locks severos de leitura/escrita, especialmente durante picos de venda como a Black Friday.
Solução: Criação do DynamoDB — separação completa dos fluxos de leitura e escrita com consistência eventual como premissa de design.
DeCandia, G. et al. (2007). Dynamo: Amazon's Highly Available Key-value Store. SOSP '07.
Netflix — Microservices + CQRS (2009 – 2012)
Problema: O monólito Oracle não sustentava a escala global de streaming. Transações ACID geravam latências incompatíveis com a experiência do usuário em novos mercados internacionais.
Solução: Migração para arquitetura de microserviços com CQRS. Cassandra e Elasticsearch para leitura de catálogo; MySQL particionado para escritas transacionais.
Netflix Technology Blog. Scaling the Netflix Data Infrastructure.
Uber — Schemaless + Cassandra (2014 – 2016)
Problema: PostgreSQL monolítico não suportava a demanda global simultânea. Contenção de locks entre escritas (pedidos de corrida) e leituras (cálculo de ETA, tarifas e mapas em tempo real) gerava timeouts e preços incorretos.
Solução: CQRS com Schemaless (baseado em MySQL) para escritas e Cassandra para leituras. Propagação via logs de eventos assíncronos.
Uber Engineering Blog. Schemaless: Uber Engineering's Scalable Datastore Using MySQL.
